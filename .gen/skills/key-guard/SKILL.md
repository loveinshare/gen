# key-guard — 找出那 5% 决定成败的代码

**key 不是"重要模块"，是"错了就全盘皆输、且换技术栈也不能重写"的那一小段逻辑。**
判定权在人，AI 只负责把候选摆到桌面上。

## 触发与不触发

**触发**

| 条件 | 例子 |
|---|---|
| 首次给项目做架构梳理 | 建 `REGISTRY.md` |
| 换语言 / 框架 / 重写核心逻辑 | 从 Python 迁到 Rust，哪段逻辑不能丢 |
| 改了数据迁移、鉴权、计费、评分等核心算法 | 改推荐权重 |
| `key-check` 报出命中，需要定级 | diff 碰了 `src/score.ts:10-80` |
| 用户问"这个项目真正关键的是什么" | 候选盘点 |

**不触发**

- 普通业务逻辑增删 → 记 `progress.md`
- 只改 UI 文案 → 不涉及 key
- 还没到需要定级的时候 → 先把候选记进"落选清单"，别急着登记

## 一、什么算 key（准入四问，全部为"是"）

1. **错误代价高**：算错/漏算会让产品结论失真（不是"报错"，是"静默算错"）。
2. **不可逆或难逆**：迁移、扣款、发券、通知、签名、去重、排序承诺。
3. **与技术栈无关**：换 Node→FastAPI→Go 仍然要保留同一套语义。
4. **有可断言的不变量**：能被写成测试或运行时断言。

只满足 1–2 条的是"重要代码"，进普通架构文档即可；**key 要克制，全项目建议 ≤15 个**，超过就失效了（人人都 key = 没人 key）。

## 二、候选发现清单（按命中即登记）

| 类别 | 典型形态 | 为什么危险 |
|---|---|---|
| 算法核心 | 打分、排序、推荐、匹配、聚合、去重 | 静默算错，无人报警 |
| 数值与精度 | 金额、比例、汇率、浮点累加、四舍五入策略 | 差一分钱即事故 |
| 时间与顺序 | 时区、夏令时、事件顺序、幂等窗口 | 只在特定日期炸 |
| 并发与一致性 | 锁粒度、乐观版本、事务边界、缓存失效 | 压测不炸、生产炸 |
| 权限与安全 | 鉴权判定、越权检查、签名/加密参数 | 错一次即失守 |
| 数据迁移 | 字段映射、默认值、回填顺序、可回滚性 | 不可逆 |
| 对外契约 | API 字段语义、分页/排序、错误码、编码 | 改了就是破坏性变更 |
| 性能主路径 | 决定响应时间上限的那段 | 优化错方向等于白做 |

**发现动作**：从入口（路由/CLI/任务）向下追 3 层，凡是"这行改了会改变业务结果"的位置，登记为 `candidate`。

## 三、守护级别（决定评审强度）

| 级别 | 判据（影响 × 不可逆） | 要求 |
|---|---|---|
| `critical` | 高 × 不可逆 | 必须有 decision + 人评审 + 双人确认 + 快照冻结 + 回归基准数据 |
| `high` | 高 × 可逆，或 中 × 不可逆 | decision + 人确认 + 回归测试 + CHANGELOG |
| `normal` | 其余 | 登记 + 测试 + CHANGELOG |

## 四、登记文件

### `architecture/agent/key/REGISTRY.md`

```markdown
| key_id | 级别 | 一句话 | 位置 | 不变量 | 验证方式 | 版本 | 状态 | confirmed_by |
|---|---|---|---|---|---|---|---|---|
| K-token-verify | critical | 令牌有效性判定 | src/auth/verify.ts:1-120 | 同一时刻最多一个有效令牌 | tests/key/token-verify.spec.ts | v1.2.0 | stable | 用户@20261115 |
```

字段规则：
- `位置` 用 `path:start-end`；漂移允许，但必须在同步时更新（drift-fix 记 CHANGELOG）。
- `不变量` 必须可断言；写不出 → 说明还没理解这个 key。
- `验证方式` 必须指向真实存在的测试或基准数据。
- `confirmed_by` 由人签字；`pending` 表示只是候选，**不享受守护**。

### `architecture/agent/key/CHANGELOG.md`（append-only，最新在上）

```markdown
| 时间 | key | 旧→新 | 原因 | 决策 | 验证 | 结果 |
|---|---|---|---|---|---|---|
| 2026111502 | K-token-verify | v1.1→v1.2 | 加 token 版本号，支持改密踢出 | D-2026111502 | tests/key/token-verify.spec.ts 全绿 + 手工复跑 50 次 | 通过 |
```

### `reviews/<TS>-<key-id>.md`

必含：变更前后行为对比（用具体输入输出，不用形容词）、受影响依赖、测试覆盖、回滚方式、人确认记录。

## 五、变更闸门

> 机械部分交给 CLI：`node .gen/scripts/gen.mjs key-check`（命中 critical/high 退出码 1）。
> 它只做"文件+行号是否落在登记区间"的比对，**判定仍需人**；但"有没有碰到"不该靠肉眼。

1. **检测**：`git diff --name-only` 与 REGISTRY 的 `位置` 求交（行号漂移时按路径兜底）。
2. 命中 `critical` / `high`：
   - 阻止静默合并（在汇报中明确"这触碰了 key，未走流程"）
   - 强制开 `decision-page`（复用多轮交互）
   - `resolved` 后写 review + CHANGELOG，人签字
   - 更新 `REGISTRY.md` 版本与 `last_changed`
3. 命中 `normal`：允许直接改，但必须更新 CHANGELOG + 有回归测试。
4. **AI 不得自行判定 key、不得自行签字、不得在 `changing` 状态下发布**。

## 六、人读版 `architecture/human/KEY.md`

由本 skill 渲染，规则（同 arch-sync 反晦涩要求）：

- 每个 key 一段：**它算什么 → 一个具体例子 → 错了会怎样 → 现在靠什么保证 → 上次改是什么时候**
- 例子必须是真实数字（脱敏），不许用 `foo/bar`
- 不出现算法术语堆叠；必须能让非本领域的人读出"这里错了会赔钱/会算错/会漏人"
- 每个 key 末尾链到 `reviews/` 最新一份

## 七、交付判定

- [ ] 候选清单已产出，每条有命中类别与一句话说明
- [ ] 每个 `confirmed` key 有不变量、验证方式、级别、签字
- [ ] key 数量 ≤15（超了要合并或降级，并说明）
- [ ] `REGISTRY.md` 位置可解析（path 存在）
- [ ] 变更走完 review + CHANGELOG
- [ ] `human/KEY.md` 已重渲染且有人读确认

## 八、反模式

- 把"整个 auth 模块"登记成 key（粒度太粗，无法守护）
- 不变量写成"令牌要安全"（不可断言）
- 只有 CHANGELOG 没有 review（不知道行为怎么变）
- key 改了但测试没覆盖不变量（守护是假的）
- 用覆盖率当守护证明（覆盖了不等于断言了不变量）
