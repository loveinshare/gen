# repair — 复现在前，根因在中，回归在后

**不许"试试看"式修补。** 不能复现的修复等于没修，只是把现象挪走了。

## 触发

- `validate` 出现 `fail`
- 线上/测试环境报错
- 用户报 bug
- 测试 `flaky`

---

## 阶段 1：复现（不做这步不许改代码）

1. **拿到最小复现**：
   - 稳定复现：写出精确步骤/命令/输入
   - 间歇复现：记录频率（`12/50`）、环境、时间相关性
   - 不可复现：**停止修复**，改为加观测（日志/断言/告警），把"不可复现"作为结论上报
2. **固化**：把复现变成可执行用例，放 `tests/` 下（哪怕先标 `skip`），或把 fixture 放 `tests/fixtures/<F-id>/`。
3. **写失败档案** `tests/failures/F-<TS>-<slug>.md`：现象、复现、期望 vs 实际、环境、影响面、初步范围。
4. **缩小范围**：二分（按输入 / 按代码路径 / 按提交历史 `git bisect`），直到能指到 **一个函数或一次提交**。

## 阶段 2：假设与定位

1. 列**假设清单**（≥2 条，否则容易确认偏误）：

```markdown
| # | 假设 | 验证方式 | 结果 |
|---|---|---|---|
| H1 | 时区转换用了本地时间 | 打印 `tz` 与入参 | 排除 |
| H2 | 并发写覆盖了计数 | 加行锁后重跑 50 次 | 成立 |
```

2. 每条假设都要有**可执行的证伪方式**；无法证伪的假设不写进去。
3. 找到根因后，用一句话写清：`因为 X，在 Y 条件下导致 Z`。写不出这句话 = 还没找到。

## 阶段 3：修复

1. 修**根因**，不是修症状。若只能修症状（成本原因），显式记录：`症状缓解，根因未除，风险：...`，并开决策或登记 `KNOWN-ISSUES`。
2. 最小 diff；不为修一个 bug 顺手重构（另开切片）。
3. 加**回归测试**：必须能在修复前失败、修复后通过。把这一步的验证记录进档案（"回退修复后该测试失败"）。
4. 若触碰 key / 契约 → 走 `key-guard` / `decision-page`，不许直接合。

## 阶段 4：验证与收尾

1. 复现用例转 `pass`；跑相关测试子集 + 之前失败的用例。
2. 更新失败档案：`status: fixed` / `mitigated`，写根因、修复提交、回归测试位置、影响面。
3. `tests/LEDGER.md` 追加一行；`progress.md` 追加一行。
4. 若同类问题出现过 ≥2 次 → 在 `architecture/human/KNOWN-ISSUES.md` 登记模式，并建议加静态检查/断言。
5. **flaky 专项**：连续 3 次同环境复跑，记录失败率；未达 3 次证据不得标 `flaky`，只能标 `unknown`。

## 交付判定

- [ ] 有可执行复现（或明确"不可复现 + 已加观测"）
- [ ] 有一句根因陈述（`因为 X，在 Y 下导致 Z`）
- [ ] 有回归测试，且证明过"修复前失败"
- [ ] 失败档案 `status` 已更新
- [ ] 台账已追加
- [ ] 没有扩大范围

## 反模式

- 直接改代码看现象是否消失（无假设、无复现）
- 把异常 `try/catch` 吞掉当修复
- 修完不写回归测试（下次必然复发）
- 把"重启后好了"当根因
- 猜测期间连续改 5 处，最后不知道哪处生效

## 与 `test-ledger` 的分工

`repair` 负责**单个缺陷的全生命周期**；`test-ledger` 负责**所有测试执行的账本与趋势**。缺陷档案写完要在台账里留一行指针。
